## Reading Memory Statistics

| Task | Command |
|---|---|
| Raw kernel-maintained memory data | `cat /proc/meminfo` |
| Human-readable summary parsed from `/proc/meminfo` | `free -h` |
| Detailed virtual memory statistics (processes, swap activity, I/O, CPU) | `vmstat 1` (refreshes every second) |

<Pitfall title="'Low Free Memory' Usually Isn't a Problem">

Linux aggressively uses otherwise-idle RAM to **cache** disk data, on the theory that free memory is wasted memory — that cache is instantly reclaimed the moment an application actually needs it. In `free -h` output, look at the **`available`** column, not `free`. A system showing 200 MB "free" but 6 GB "available" is healthy; the rest is reclaimable cache, not memory under real pressure.

</Pitfall>

## When Memory Runs Out: The OOM Killer

When a system is critically low on memory — genuinely out, not just low on the "free" column — the kernel's **OOM (Out-Of-Memory) Killer** decides which process to forcibly terminate to reclaim enough RAM to keep the system responsive. It scores every process (weighing memory usage, priority, and process age) and kills whichever one scores worst, logging the event to the kernel ring buffer (`dmesg`) and the system journal.

Swap space directly delays this outcome: it lets the kernel page out less-active memory to disk instead of killing a process outright, buying time when the system (or a specific application) is requesting more memory than physical RAM provides. But swap is not a substitute for adequate RAM — once swap itself is exhausted, or the system is thrashing (constantly paging in and out under heavy load), the OOM killer activates regardless.

<Pitfall title="Find OOM Kills in the Logs, Not Just Symptoms">

A service that "just disappeared" with no crash log of its own is a classic OOM-kill symptom. Check `dmesg | grep -i "out of memory"` or `journalctl -k | grep -i oom` before assuming a software bug — the kernel logs exactly which process it killed and why.

</Pitfall>

## Diagnosing CPU vs. Memory Bottlenecks

| Symptom | Likely cause | Where to look |
|---|---|---|
| High load average, low CPU usage in `top` | Processes stuck waiting on I/O (disk or network), not actually CPU-bound | Process state `D` in `ps`; check `iostat` |
| High CPU usage from one process | A runaway or looping process | `top` sorted by `%CPU`, then investigate that specific PID |
| High swap activity (`si`/`so` columns in `vmstat` constantly non-zero) | The system is under real memory pressure and actively paging | `free -h` `available` column, `vmstat` |
| Services disappearing without a crash log | OOM killer activity | `dmesg`, `journalctl -k` |

**Common process-level issues to recognize:** a **runaway process** consumes CPU without bound (fix: `renice` it down, or `kill` it); a **zombie process** (see Lesson 1) indicates a parent that isn't reaping children; **memory leaks** show as a single process's resident memory climbing steadily over time in repeated `ps`/`top` snapshots without ever releasing it back.
