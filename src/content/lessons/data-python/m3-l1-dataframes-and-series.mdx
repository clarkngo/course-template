## Loading a CSV

```python
import pandas as pd

sales = pd.read_csv("corner_cafe_sales.csv")
print(sales)
```

One line replaces `csv.DictReader`, the loop, and the manual `int()`/`float()` conversions from Module 2 — `read_csv` does all three, inferring each column's type by scanning the values. The object it returns, `sales`, is a **DataFrame**: a table, with rows and named columns, that behaves a lot like the list-of-dicts you built by hand, but with far more built-in operations.

`import pandas as pd` is a near-universal convention — virtually every pandas codebase you'll ever read uses `pd` as the alias, so use it too.

## Inspecting What You Loaded

Before doing anything else with a new dataset, look at it. Four methods cover almost every first look you'll need:

```python
sales.head()      # first 5 rows
sales.info()      # column names, types, non-null counts
sales.dtypes      # just the type of each column
sales.shape       # (rows, columns) as a tuple
```

`sales.head()` shows you the first five rows, so you can sanity-check that the file loaded the way you expected. `sales.info()` is the most useful single call for a new file — it lists every column with its inferred type and how many non-missing values it has, which is often the fastest way to spot a problem before it becomes a bug three steps later. `sales.dtypes` on this file should show `date` and `item` as `object` (pandas' name for text), and `quantity` and `price` as numeric (`int64` and `float64`) — confirmation that the conversion Module 2 made you do by hand happened automatically here.

## DataFrames Are Made of Series

Select a single column with square brackets and a column name, and you get back a **Series** — a single labeled column of data, the building block a DataFrame is made from:

```python
>>> sales["item"]
0        Latte
1     Espresso
2       Muffin
3    Cold Brew
...
Name: item, dtype: object
```

That number on the left of each value is the **index** — a label for each row, `0, 1, 2, ...` by default, similar in spirit to a list's position but usable as a lookup key even after rows are filtered or reordered.

Select more than one column by passing a *list* of names, which gives you back a DataFrame, not a Series — the double brackets are doing two different jobs, an outer `[]` for "select columns" and an inner `[]` for "here's a list":

```python
sales[["item", "price"]]
```

## Selecting Rows: `.loc` and `.iloc`

Columns are selected by name; rows are selected with `.loc` (by index label) or `.iloc` (by integer position). For the default `0, 1, 2, ...` index, they usually agree, but they mean different things:

```python
sales.loc[0]        # row labeled 0
sales.iloc[0]        # the first row by position
sales.iloc[0:3]       # first three rows by position
```

The distinction matters once a DataFrame's index isn't a plain row count anymore — after sorting, filtering, or setting a column as the index, `.loc[0]` still means "the row labeled `0`," which may no longer be the first row. `.iloc` always means position, no matter what the labels say. You'll use boolean filtering far more than either once Module 4 gets going, but both are worth knowing now.

<Pitfall title="Single Brackets vs Double Brackets">

`sales["item"]` and `sales[["item"]]` look almost the same and return different types — one a Series, one a one-column DataFrame — which matters the moment you chain another operation onto the result.

```python
# This is a Series — .sum() works directly on it
sales["quantity"].sum()

# This is a one-column DataFrame — .sum() still works,
# but returns a Series (a sum *per column*, here just one),
# not a single number
sales[["quantity"]].sum()
```

Neither is "wrong," but they're not interchangeable. If you want a single scalar value back — one number, one total — reach for single brackets and a column name. If you want to keep the result as a table (to select several columns at once, or to add a computed column back in), use double brackets. Mixing them up doesn't usually crash your program; it just produces a result shaped differently than you expected, which is a quieter and harder bug to spot.

</Pitfall>

<Quiz question="sales.dtypes shows the item column as dtype object instead of something like 'string'. Is that a bug in how the CSV loaded?">
<div>

**No — `object` is simply pandas' dtype label for a column holding text (or, more precisely, arbitrary Python objects, which in practice is almost always strings for a CSV column).**

pandas dtypes map onto a small set of underlying types: `int64` and `float64` for numbers, `bool` for booleans, `datetime64` for parsed dates, and `object` for everything else — which in a freshly-loaded CSV means text columns. It's not a sign anything went wrong; `date`, `item`, and any other text column will show `object` by default. You'll see this again in Module 3's next lesson, when a numeric column shows up as `object` too — *that* is the real warning sign, because it usually means the column has a stray non-numeric value (a stray space, a typo, a missing entry written as text) that stopped pandas from inferring a numeric type for the whole column.
